# 專案企劃：AI 逆轉法庭：證詞的破綻

## 專案目標

使用生成式 AI 與固定規則，製作一款可透過網址分享、在瀏覽器遊玩的法庭推理遊戲。玩家扮演辯護律師，從證人說法和案件證據中找出矛盾。

## 已確認的 MVP

| 項目 | 規劃 |
| --- | --- |
| 案件 | 一個虛構的美術館名畫失竊案，暫名「消失的名畫」 |
| 玩家 | 被告辯護律師 |
| 證人 | 三位，個性與所知資訊不同 |
| 證據 | 五項，玩家可查看並在庭上出示 |
| 互動 | 玩家自由提問；AI 扮演證人及法庭角色回應 |
| 推理 | 玩家選擇一段證詞和一項證據；Python 依固定答案驗證矛盾 |
| 狀態 | 每位玩家的對話、證據與進度彼此獨立 |
| 結局 | 至少有成功揭露真相與未能證明案件兩種結果 |

## 一局遊戲流程

1. 閱讀案件背景與被告資訊。
2. 查看目前可用的證物。
3. 詢問證人，從回答中尋找需要追問的說法。
4. 選擇證詞並出示證物。
5. Python 檢查這組證詞與證物是否矛盾，再更新遊戲進度。
6. AI 依程式提供的結果生成角色反應。
7. 玩家提出最後推理，進入相應結局。

## 技術分工

| 元件 | 職責 |
| --- | --- |
| Python | 固定案件資料、證據驗證、回合與結局規則 |
| Streamlit | 瀏覽器介面、玩家工作階段、部署入口 |
| Gemini API | 依已知角色設定和程式驗證結果生成對話 |
| GitHub | 保存程式與供其他 AI 閱讀的企劃文件 |
| Streamlit Community Cloud | 預定的免費公開網站部署平台 |

## 安全與額度控制

- Gemini API Key 僅存於 Streamlit 部署 Secrets；公開 GitHub 儲存庫不得包含金鑰。
- 限制單次輸入長度及每局 AI 呼叫數，避免免費額度快速耗盡。
- API 失敗或額度用盡時，以固定角色回應維持遊戲可玩性。
- 遊戲採虛構案件；不收集玩家個人資料。
- 使用玩家自己的 Streamlit 工作階段保存狀態，不把一位玩家的資料提供給其他玩家。

## 案件內容狀態

案件主題與玩家身分已確定。此前討論曾用「策展人聲稱閉館後一直在辦公室，門禁紀錄卻顯示 20:02 進入展廳」作為矛盾示例；此例目前僅為玩法示意，尚未定為正式劇情。其他證人、真相、證詞、證據配對及結局規則都待設計與確認。

## 建議開發順序

1. 定稿案件真相、三位證人、五項證據及正確矛盾配對。
2. 先完成不呼叫 AI 也能從頭玩到結局的規則版。
3. 加入 Gemini 角色對話、請求限制與備援回應。
4. 整理 Secrets 與部署設定，部署到 Streamlit Community Cloud。
5. 用公開網址確認新玩家可各自獨立遊玩。
